# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Arcade Vault: a platform to play games online and compete for the highest score. It follows Spec Driven Design (`/spec` and `/spec-impl` skills). Specs 01–12 are all `Implemented`; game-jam specs live in `specs/game-jam/<id>/` (each has a `README.md`; see the spec's `Status` line).

Routes: `/` (home), `/games` (library with category filter), `/games/[id]` (detail + leaderboard), `/games/[id]/play` (player), `/hall-of-fame`, `/about` (contact form), `/login` (sign in / create account), `/forgot-password`, `/reset-password` (needs a session), `/onboarding` (needs a session; one-time username choice), `GET /auth/confirm` (email link handler), `GET /auth/callback` (OAuth return), `GET /api/health`.

Playable games: see the catalog in [Implemented games](references/implemented-games.md). To add a new one, follow the `/new-game` integration contract (`.claude/skills/new-game/integration-contract.md`).

## Commands

- `npm run dev` — dev server (Turbopack)
- `npm run build` / `npm start` — production build / serve
- `npm run lint` — ESLint (flat config, `eslint.config.mjs`)
- `npm run format` — Prettier (`trailingComma: "all"`)
- `npm run db:types` — regenerate `types/supabase.ts` from the remote schema
- `npm run db:push` — apply `supabase/migrations/` to the remote project
- No test runner is configured yet.

First time on a machine: `npx supabase link --project-ref ekupeshkawfihlnpmpvi` (needs `SUPABASE_ACCESS_TOKEN`).

## Spec workflow and skills

- Specs live in `specs/NN-<slug>.md`. Status flow: `Draft` → `Approved` → `Implemented`. `specs/.spec-config.yml` has `AutoCreateBranch: true`, so `/spec-impl` creates and switches to a `spec-NN-slug` branch; each spec is merged through a PR.
- `/spec` and `/spec-impl` come from `Klerith/fernando-skills` (`npx skills@latest add Klerith/fernando-skills`). They live in `.claude/skills/` (mirrored in `.agents/skills/`) and are tracked in `skills-lock.json`.
- `/new-game <references/started-games folder | description>` specs a new playable game with its leaderboard. It builds on `/spec`, writes `specs/NN-<id>-game.md` in `Draft` and stops; implement it afterwards with `/spec-impl`. It is user-invoked only. Its `integration-contract.md` (in `.claude/skills/new-game/`) is the authoritative contract for adding a game.
- `/spec-impl-game <NN-spec>` is `/spec-impl` for game specs: it reads and follows `.claude/skills/spec-impl/SKILL.md` (same gates, branch and step-by-step pauses), and when the implementation is done it launches `skin-designer` and then `mobile-porter` on the game, **sequentially** (never in parallel), followed by `tsc`, lint and build. It is user-invoked only.
- `/skin-designer <id...|all>` makes sure the games have the `classic`, `neon` and `retro` skins. Subagents cannot launch subagents, so this skill launches one `skin-designer` per game **in parallel**, then runs `tsc`, lint and build once. It is user-invoked only.
- Game-jam specs (`specs/game-jam/<id>/`, written by the `game-jam` agent) are phased (`01-<id>-core.md`, `02-…`); implement them with `/spec-impl` or `/spec-impl-game`.
- User-level skills (in `~/.claude/skills/`): always use `/frontend-design` for UI; `/worktree <instructions>` runs a task in an isolated git worktree in `.trees/`.

## Subagents

Project subagents live in `.claude/agents/` (tools, write scope and rules are in each definition file).

- `game-planner` ([definition](.claude/agents/game-planner.md)): scores 2–3 candidates for the next game and recommends one with a ready `/new-game` command. Has project memory and maintains `references/game-suggestions-todo.md`. Use it **before** `/new-game`.
- `game-jam` ([definition](.claude/agents/game-jam.md)): turns a game description into 2–3 phased `Draft` specs in `specs/game-jam/<id>/`. Autonomous; never writes code.
- `skin-designer` ([definition](.claude/agents/skin-designer.md)): adds the missing `classic` / `neon` / `retro` skins to **one** game inside `lib/games/<id>/`. For several games use `/skin-designer`.
- `mobile-porter` ([definition](.claude/agents/mobile-porter.md)): audits and fixes **one** game's touch/mobile layout against SPEC 11 with Playwright (375×812 and 1440×900). Run one game at a time.
- `security-auditor` ([definition](.claude/agents/security-auditor.md)): read-only audit of the database (RLS, policies, grants, SECURITY DEFINER functions, advisors, migration drift) and the app (headers, `proxy.ts` route protection, Server Actions, redirects, secrets, `npm audit`). Has project memory and keeps `references/security-report.md` with stable `SEC-NNN` findings. Modes: `full`, `db`, `app`, `diff`, `accept SEC-NNN <reason>`, `resolve SEC-NNN`. Never edits code or applies migrations; implement its recommendations through `/spec`. Run it after changes to auth, migrations, Server Actions, route handlers, `proxy.ts` or `next.config.ts`, and before merging a PR.

## Architecture notes

- App Router only (`app/`). Root layout types its props with the global `LayoutProps<"/">` helper (no import needed), generated by Next typegen.
- `next.config.ts` enables `cacheComponents`, `partialPrefetching` and `experimental.agentFeedback`. Cache Components changes data-fetching and caching semantics, so check the docs before using dynamic APIs or fetching data.
- Components: route-shared ones in `app/_components/` (subfolders `home/`, `about/`, `games/`).
- Server data in `app/data/` (`games.ts`, `scores.ts`, `activity.ts`) uses `"use cache"` with `cacheTag("games" | "scores")` and `cacheLife("hours")`. `categories.ts` is client-safe on purpose (no server-only imports).
- Server Actions:
  - `app/games/[id]/play/actions.ts` — `saveScore(gameId, score)` calls the `submit_score` RPC (the player comes from the session, never from the client), then `updateTag("scores")` and `updateTag("games")`.
  - `app/hall-of-fame/actions.ts` — `getMyBests()` (the signed-in player's best per game; `{}` for guests).
  - `app/login/actions.ts` — `signUp`, `signIn`, `signOut`, `requestPasswordReset`, `updatePassword` (state types in `app/login/auth-state.ts`; a `"use server"` file can only export async functions).
  - `app/onboarding/actions.ts` — `setUsername`, which calls the `set_username` RPC (reuses `AuthFormState`).
  - `app/about/actions.ts` — `sendContactMessage` via Resend, with `emails/contact-email.tsx` rendered through `render()`.
- Session: `SessionProvider` / `useSession` is client-only and exposes `{ user: { id, name, needsUsername } | null, status: "loading" | "ready", needsUsername, signOut }`. It reads the Supabase session with the browser client (`getUser()` + `onAuthStateChange`) and loads `profiles.username` as `name` (placeholder `PLAYER` and `needsUsername: true` while it is null); it re-checks the session on route changes while signed out or without username, because a Server Action redirect (sign-in, onboarding) does not remount it. With `needsUsername`, Nav shows `CHOOSE NAME` and the GAME OVER modal links to `/onboarding?next=/games/<id>/play` instead of SAVE SCORE.
- OAuth (SPEC 14, Google and GitHub): `AuthForm` calls `signInWithOAuth` with `redirectTo = <origin>/auth/callback?next=<safe next>`; `app/auth/callback/route.ts` exchanges the code, then goes to `/onboarding?next=…` when `profiles.username` is null, otherwise to `next`; errors go to `/login?error=oauth`. `/onboarding` calls `set_username(p)` (security definer, `authenticated` only, sets the name once, no rename). Dashboard setup (manual): Google Cloud OAuth client and GitHub OAuth App with callback `https://ekupeshkawfihlnpmpvi.supabase.co/auth/v1/callback`; enable both in Auth → Providers; add `/auth/callback` to the redirect URLs (local and production).
- Auth (SPEC 13, Supabase Auth email + password): `proxy.ts` + `lib/supabase/proxy.ts` refresh the session cookies and (SPEC 15) protect private routes: `updateSession` returns `{ response, user }` (user id from `getClaims()`, no extra call) and `proxy.ts` redirects guests using `PROTECTED_ROUTES` in `lib/auth/routes.ts` (`/onboarding` → `/login?next=/onboarding`, `/reset-password` → `/forgot-password`; exact or sub-path match; the redirect carries the refreshed cookies and cache headers). To make a route private, add one entry to that map. The per-page and Server Action checks stay as defense in depth (username and recovery-session rules; `getClaims()` is local, so only `getUser()` is authoritative). Public by design: `/`, `/games`, `/games/[id]`, `/games/[id]/play`, `/hall-of-fame`, `/about`, `/login`, `/forgot-password`, `/auth/*`, `/api/health`. Sign-up requires a unique username (`^[A-Z0-9_]{1,10}$`, stored uppercase in `profiles`) and a password of at least 8 characters with a lowercase letter, an uppercase letter, a number and a symbol (`validatePassword` / `PASSWORD_REQUIREMENTS`, mirroring the Supabase dashboard rule; sign-in is not affected); rules are shared in `lib/auth/validation.ts` (client-safe, includes `safeNext` for `?next=`) and enforced again by the actions and the database. Email links (confirm signup, reset password) land on `app/auth/confirm/route.ts`. Read the session only in dynamic code or inside `<Suspense>`, never inside `"use cache"`. Guests can play but cannot save scores. Auth screens share `app/_components/auth-ui.tsx`.
- Auth dashboard setup (manual, not in code): Auth → Email: confirm email on, minimum password 8 and password requirements "lowercase, uppercase letters, digits and symbols" (keep in sync with `validatePassword`; if they drift users see Supabase's `weak_password` message); Auth → Rate Limits: sign-ups and sign-ins 10 per 5 minutes per IP; leaked password protection is off (Free plan, accepted risk); URL Configuration: Site URL plus `http://localhost:3000/**` and the production URL; Confirm signup / Reset password templates linking to `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=signup` and `…&type=recovery&next=/reset-password`; custom SMTP with Resend (without a verified domain it only delivers to the account owner).
- Security headers (SPEC 15): `next.config.ts` `headers()` sends `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin` and a restrictive `Permissions-Policy` on every route, plus `Strict-Transport-Security: max-age=63072000; includeSubDomains` only when `NODE_ENV === "production"` (so `next dev` does not send it; it is read at startup, restart the dev server after changing it). No CSP yet (needs nonces with Cache Components; future spec). `DENY` blocks embedding the site in any iframe.
- Styling: Tailwind CSS v4, wired through a custom Turbopack rule in `next.config.ts` (`@tailwindcss/turbopack` loader for `*.css`). The theme is dark-only retro/neon in `app/globals.css`: tokens on `:root`, exposed to Tailwind via `@theme inline` (`bg`, `ink`, `cyan`, `magenta`, `yellow`, `green`, `gold`, `font-pixel`, `font-mono`…), plus many hand-written classes (`.btn`, `.crt`, `.hud-stat`, `cover-*`…).
- Fonts: Press Start 2P, JetBrains Mono and Courier Prime via `next/font/google`, exposed as CSS variables in the root layout.
- TypeScript is `strict`. Path alias `@/*` maps to the repo root (not `src/`).

## Supabase

- Two projects: Dev (`ekupeshkawfihlnpmpvi`, the only one Claude Code can reach through MCP/CLI) and Production (owned by the user; Claude has **no access** and must never ask for its ref, password or keys). Never run `supabase link`, `config push` or `db push --db-url`. The user deploys to Prod with `docs/production-runbook.md` and checks it with `supabase/checks/verify-prod.sql`; keep that check's expected migration list in sync when adding migrations.
- Clients (typed with `Database` from `types/supabase.ts`, which is generated: never edit by hand):
  - `lib/supabase/server.ts` — `await createClient()` for Server Components, Server Actions and Route Handlers (dynamic contexts only, not inside `"use cache"`).
  - `lib/supabase/client.ts` — `createClient()` for Client Components.
  - `lib/supabase/public.ts` — `createPublicClient()`, cookie-less, safe inside `"use cache"` for public reads.
  - `lib/supabase/env.ts` — validates the environment variables.
- Schema (`supabase/migrations/`): tables `games`, `scores` (RLS: readable by everyone; `user_id` references `auth.users`; writes only through `submit_score(p_game_id, p_score)`, executable by `authenticated` only, which takes the player from `profiles.username`) and `profiles` (one row per auth user, created by the `handle_new_user()` trigger; RLS lets a user read only their own row; `username` is nullable until chosen), RPC `username_available(p)`, views `games_with_best`, `player_bests`, `top_players_today`. Scores are integers in `0..9,999,999`.
- Accepted security linter warnings (SPEC 15), all SECURITY DEFINER RPCs callable through `/rest/v1/rpc` by design: `submit_score(p_game_id, p_score)` (`authenticated` only; takes the player from the session), `set_username(p)` (`authenticated` only; sets the name once) and `username_available(p)` (`anon` + `authenticated`; returns only a boolean, needed by sign-up before a session exists). `rls_auto_enable()` is revoked from `public`, `anon` and `authenticated` by migration (not dropped, so automatic RLS on new tables keeps working; re-run the migration if the dashboard recreates it). RLS is enabled on `games`, `scores` and `profiles`. The only other warning is leaked password protection (Free plan).
- A new game only needs a seed migration; `games`, `scores`, `submit_score`, the views and `saveScore` are generic per `game_id`.
- Env vars: copy `.env.example` to `.env.local` (Supabase URL and publishable key, `SUPABASE_ACCESS_TOKEN` for the CLI only, Resend vars for the contact form). Never add a secret / service-role key to the code or env files.
- `GET /api/health` checks that Supabase is reachable (`200 {ok, latencyMs}` or `503`).

## Game platform (`lib/games/`)

- `types.ts` — `GameEngine` (`pause`, `resume`, `end`, `restart`, `destroy`), `BaseSnapshot` (`score`, `state`), `GameCallbacks` (`onChange` only when a field changes, `onGameOver` once per game over).
- `registry.ts` — `defineGame<S>()` entries keyed by `games.id`: lazy `load`, `initialSnapshot`, `hud`, `controls`, `ariaLabel`, optional `sound` and a required `touch` layout (`dpad` arrows, action `buttons`, `repeat` codes). A catalog row with no entry renders "NOT PLAYABLE YET".
- `shared/input.ts` and `shared/audio.ts` (global mute flag, muted by default, `createSoundBank`).
- `shared/virtual-keys.ts` — `createVirtualKeys()` dispatches synthetic `keydown`/`keyup` on `window` (ref-counted, with auto-repeat). `app/_components/games/touch-controls.tsx` uses it for the on-screen D-pad and buttons, shown only under `(hover: none) and (pointer: coarse)`; engines need no touch code.
- `shared/skins.ts` — skin ids (`classic` default, `neon`, `retro`); a game declares `skins` in `GameOptions` (`types.ts`) and implements them in its own `skins.ts`. `GamePlayer` has the SKIN selector and saves the choice in `localStorage` as `av:skin:<id>`.
- Each game has its own folder (`constants.ts`, `types.ts`, `engine.ts`, `skins.ts`, plus `entities`, `levels`, `pieces`, `lanes` or `sprites` as needed). Static assets go in `public/games/<id>/`.
- `GamePlayer` and `app/_components/games/game-canvas.tsx` own the score HUD, Pause (`P` / `Esc`), Mute (`M`), the GAME OVER modal and score saving. Engines must not draw or handle those.
- To add a game: `/new-game` → review and approve the spec → `/spec-impl-game`.
